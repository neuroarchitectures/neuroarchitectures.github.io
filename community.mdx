## How to propose a specification change

1. Read the [specification](/specification/introduction) and search [existing issues](https://github.com/neuroarchitectures/naxs/issues) to avoid duplicates.
2. Open an issue with the **Specification feedback** template describing the problem and your proposal.
3. For accepted changes, fork the repository and branch from `main`.
4. Update `specification.md` — and `naxs/v0.1/schema.json` plus `pynaxs` if validation behavior is affected.
5. Ensure the validator test suite passes:

   ```bash
   cd pynaxs && pip install -e . && python -m pytest tests/
   ```

6. Open a pull request referencing the related issue.

Full details are in [CONTRIBUTING.md](https://github.com/neuroarchitectures/naxs/blob/main/CONTRIBUTING.md).

## Registering a new operator type

The operator type registry grows through community proposals (per §11.2 of the specification):

1. Define the type **name** (camelCase), **description**, expected **parameters**, and input/output **arity**.
2. Provide **at least 3 real-world architecture examples** that use the type.
3. Open an issue with the **Register an operator type** template.
4. If accepted, the type ships in the next minor version of the spec.

## Governance

- **Major** versions (1.0 → 2.0): breaking changes to required fields or semantics — require broad consensus.
- **Minor** versions (1.0 → 1.1): new optional fields, operator types, and standard metadata keys.
- **Patch** versions: clarifications, documentation fixes, and schema corrections.
