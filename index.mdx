# The open format for neural architecture exchange

**NAXS** (Neural Architecture Exchange Specification) defines a **vendor-independent, framework-agnostic JSON format** for describing neural network architectures as directed graphs of typed, parameterized components.

Any tool, vendor, research group, or automated agent can produce or consume a NAXS document to share, compare, transform, or analyze a neural architecture — without depending on a specific framework.

## What is a NAXS document?

A NAXS document is a single JSON file that describes an architecture as a **directed graph** of typed, parameterized components:

```text
my-architecture.naxs.json
├── spec_version        # "1.0"
├── id / name           # identity & display
├── components[]        # graph nodes — typed operators with parameters
├── connections[]       # graph edges — explicit data flow
├── block_templates[]   # optional — reusable subgraphs & repetition (§25)
└── metadata / provenance
```

The smallest valid document is about 10 lines of JSON:

```json
{
  "spec_version": "1.0",
  "id": "minimal-mlp",
  "name": "Minimal MLP",
  "components": [
    {
      "id": "n1",
      "type": "input",
      "name": "x",
      "params": { "shape": [10] },
      "inputs": [],
      "outputs": ["n2"]
    },
    {
      "id": "n2",
      "type": "linear",
      "name": "fc1",
      "params": { "inFeatures": 10, "outFeatures": 5 },
      "inputs": ["n1"],
      "outputs": []
    }
  ],
  "connections": [
    { "id": "c1", "from": "n1", "to": "n2" }
  ]
}
```

## Why NAXS?

<CardGroup cols={3}>
  <Card title="Framework-independent" icon="shuffle">
    Operator types are referenced by name (`conv2d`, `multiHeadAttention`), not by framework API. PyTorch configs, JAX models, and vendor graphs all map to one format.
  </Card>
  <Card title="Graph-first" icon="git-fork">
    Connectivity is explicit — never implicit in code structure. Fan-in, fan-out, and even cyclic (recurrent) topologies are first-class.
  </Card>
  <Card title="Human-readable" icon="book-marked">
    A valid document can be as small as 10 lines of JSON, hand-authored without specialized tooling — yet structured enough for automated analysis.
  </Card>
</CardGroup>

Two more properties make NAXS practical at scale:

- **Extensible by design** — unknown fields are preserved, not rejected. Vendors can embed custom metadata without forking the spec.
- **Compression through reuse** — block templates and `repeat` directives turn a 12-layer transformer into 7 components instead of 51 (see [§25](/specification/block-templates)).

## How does NAXS work?

NAXS documents flow through three stages:

<CardGroup cols={3}>
  <Card title="1. Author" icon="pencil-line">
    Describe the architecture as a JSON graph — by hand, by export from a framework, or generated by a tool.
  </Card>
  <Card title="2. Validate" icon="check-circle-2">
    Check the document against the JSON Schema or the `pynaxs` reference validator: structural integrity, connection consistency, parameter validity.
  </Card>
  <Card title="3. Exchange" icon="share-2">
    Share the document between tools and teams. Compare architectures, compute parameter budgets, visualize topology, or lower to a runtime format.
  </Card>
</CardGroup>

NAXS is **not** an execution format (like ONNX), a training configuration (like PyTorch Lightning YAML), or a compiler IR (like MLIR). It is an **architecture topology exchange format**: it describes *what the architecture is* — components, parameters, connectivity — without prescribing *how* it runs. See [how NAXS relates to other formats](/specification/introduction#3-relationship-to-other-formats).
